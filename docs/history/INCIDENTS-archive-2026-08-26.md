# INCIDENTS.md — Suivi des incidents projet

Ce document trace les incidents **techniques/projet** (bugs, pannes, régressions) rencontrés au cours du développement de XRent Manager. Il ne concerne pas les incidents métier liés à une location (dommage véhicule, accident, litige client) — ceux-ci relèveront d'un module métier dédié, dont les règles sont à définir dans [DOMAINRULES.md](./DOMAINRULES.md).

Cinq incidents sont enregistrés ci-dessous : INC-1 (technique/process, environnement de développement, Sprint 15), INC-2 (bug applicatif de stabilité, hydration mismatch, Sprint 21, résidu résolu au 2026-08-17), INC-3 (infrastructure de test, blocage intermittent du serveur `next dev` partagé, Sprint 24-2, réduit au Sprint 24-3, investigation complémentaire toujours réduit, nouvelle tentative de résolution complète au Sprint 24-4 — toujours réduit, non résolu ; réduit à l'usage recommandé au Sprint 24-5 via `scripts/test-grouped.mjs` ; deux attributions erronées ultérieures corrigées, Sprint 31A et Sprint 13E tâche 2 (partie 1), chacune révélant un bug applicatif distinct sans rapport avec INC-3 lui-même ; cause racine réelle démontrée et corrigée à la source, INC-3 déclaré clôturé au Sprint 13E tâche 1 (suite finale) ; **nouvelle occurrence isolée observée le 2026-08-25 (second passage F-2/F-3), signature réseau pure (`ECONNREFUSED`/`SocketError`), non reproduite sur 2 exécutions suivantes de la commande brute ni sur 2 exécutions du runner recommandé — statut révisé de « clôturé » à « très majoritairement stable, non garanti à 100 % pour l'usage direct de `npx vitest run` »** ; **sprint de stabilisation technique du 2026-08-25/26 : trois causes contributives réelles trouvées, deux corrigées, une identifiée mais non corrigée (hors périmètre applicatif) — (1) réutilisation de connexion TCP obsolète côté client de test, corrigée ; (2) base de test `xrent_test` désencombrée de 4384 tenants orphelins, corrigée ; (3) démontrée par profilage CPU V8 réel (`--cpu-prof`) : 62,5 % du temps CPU du serveur de test passé dans `_encipher` (chiffrement Blowfish pur JavaScript de `bcryptjs`, coût 12) — corrigée par un coût bcrypt configurable (`BCRYPT_COST`, `.env.test` uniquement, production inchangée à 12), avec validation explicite du propriétaire du projet (modification de code d'authentification). **Poursuite d'investigation (même sprint, sur demande explicite de ne pas déclarer le résultat suffisant)** : cause dominante identifiée avec certitude par lecture directe du code source de Next.js (pas seulement par profilage) — `getStaticPathsWorker()` (`node_modules/next/dist/server/dev/next-dev-server.js`) crée un processus worker neuf et le détruit à **chaque** rendu d'une page à segment dynamique (`[id]`), sans jamais le réutiliser (commentaire du code source lui-même : « we don't re-use workers ») ; un warm-up séquentiel de toutes les pages avant les tests, testé et mesuré, n'a montré aucune réduction fiable (variance naturelle déjà supérieure à l'effet mesuré) et a été retiré. Une deuxième cause distincte, `experimental.devValidationWorker` (validation dev des « Cache Components », gated par un flag officiel et documenté, fonctionnalité confirmée totalement absente de ce projet), a été désactivée sans risque. Ces deux pistes touchent uniquement le comportement interne du serveur `next dev`/Turbopack en mode développement — jamais du code applicatif, jamais la production. **Deux bugs de test réels et distincts, sans aucun rapport avec le réseau, ont aussi été trouvés et corrigés en cours de route** (comptage global non scopé par tenant dans `invoices.test.ts`, ordre de nettoyage `AuditLog`/`Tenant` incorrect dans `data-reset.test.ts` face au CRON global des alertes) — voir TESTREPORT.md pour le détail. **Résolution finale (même sprint, session dédiée à l'architecture Vitest, sur exigence explicite de conserver `npx vitest run` comme unique commande officielle)** : sonde empirique dédiée démontrant que le pool `forks` de Vitest (`isolate: true` par défaut) démarre déjà un processus OS neuf pour **chaque fichier de test**, jamais réutilisé (8 fichiers testés → 8 PID distincts, aucun état partagé) — un serveur `next dev` persistant par worker (architecture envisagée en premier) n'est donc pas réalisable. Cause confirmée : ce n'est pas le nombre total de workers `jest-worker` créés par Next.js qui pose problème (il ne peut pas être réduit, comportement interne non configurable), mais le **pic de créations concurrentes** sous le parallélisme par défaut de Vitest (`maxWorkers: 4`, jusqu'à 4 fichiers de test actifs simultanément contre le même serveur partagé). **Corrigé** : `fileParallelism: false` ajouté à `vitest.config.mts` — sérialise l'exécution des fichiers de test (un seul actif à la fois contre le serveur partagé), éliminant structurellement tout pic de charge concurrente, quel que soit le nombre de workers Next.js créés pour chaque rendu individuel. **Résultat mesuré : 10/10 exécutions consécutives parfaites de `npx vitest run`** (1280/1280 à chaque fois, 0 timeout, 0 `ECONNREFUSED`/`ECONNRESET`/`SocketError`, 0 redémarrage watchdog, 0 processus/port résiduel) — objectif chiffré strict enfin atteint, sans quitter la commande officielle, sans script séparé. Coût mesuré : suite ~2x plus lente en exécution directe (~88s contre ~45s en parallèle) mais toujours très largement plus rapide que l'état de départ du sprint (~280-330s). `node scripts/test-grouped.mjs` reconfirmé 100 % fiable (2/2, 1280/1280, ~149s — plus lent lui aussi puisque chaque groupe hérite désormais de la même sérialisation, mais toujours fiable). **INC-3 est déclaré résolu pour `npx vitest run`, y compris en usage direct, pour la première fois depuis son origine (Sprint 24-2)** — voir le complément détaillé ci-dessous pour l'analyse complète, les architectures écartées et les mesures avant/après), INC-4 (test de concurrence intermittent en exécution isolée, `locations.test.ts`, identifié Sprint 34 étape 3, **corrigé à la source Sprint 34 tâche 1**, revalidé Sprint 13E tâche 1 (suite) et tâche 2 — voir détail ci-dessous) et INC-5 (documentation/outillage de test, désynchronisation silencieuse de `scripts/test-grouped.mjs` avec `src/__tests__/`, 36 tests jamais exécutés par le runner recommandé pendant plusieurs sprints, **identifié et corrigé à la source Sprint technique 4** — voir détail ci-dessous).

## Structure d'un incident

Chaque incident futur devra être consigné ci-dessous en suivant ce gabarit :

```
## INC-<numéro> — <titre court>

- **Date** : <AAAA-MM-JJ>
- **Environnement** : <développement | test | staging | production>
- **Gravité** : <critique | majeure | mineure | cosmétique>
- **Description** : <description factuelle de l'incident>
- **Impact** : <utilisateurs/tenants/données concernés, durée>
- **Cause** : <cause identifiée, ou "en cours d'investigation">
- **Correction** : <description de la correction apportée, ou "non corrigé">
- **Test de non-régression** : <référence du test ajouté, ou "à ajouter">
- **Statut** : <ouvert | en cours | corrigé | clôturé>
- **Validation finale** : <nom/rôle du validateur et date, ou "en attente">
```

## INC-8 — BUG-001 : modale de création d'un groupe de permissions dépassant le viewport (aucun défilement interne)

- **Date** : identifié lors d'une session de campagne de validation manuelle interrompue par la limite de session (rapport jamais écrit sur disque — reconstitué et corrigé le 2026-08-26), corrigé le 2026-08-26.
- **Environnement** : développement (`xrent_dev`), reproduit et vérifié en navigateur réel (Chromium via Playwright) sur un tenant de test jetable créé pour cette seule vérification, supprimé après coup.
- **Gravité** : mineure (aucune donnée ni permission affectée — défaut d'ergonomie/accessibilité, pas un défaut de sécurité), mais bloquant en usage réel : le bouton « Créer » et plusieurs catégories de permissions devenaient inatteignables.
- **Module** : `src/app/dashboard/permission-groups/PermissionGroupsPanel.tsx` (modale de création d'un groupe de permissions).
- **Préconditions** : viewport de hauteur normale (desktop ≤ ~900px de haut, ou tablette/mobile), tenant avec le jeu complet de catégories de permissions (`src/lib/permissions.ts` — une vingtaine de catégories).
- **Données utilisées** : tenant jetable créé pour la vérification (`BUG001 Verif`, supprimé après coup — voir Correction) ; aucune donnée de la campagne RAK/CASA impliquée.
- **Scénario de reproduction** : ouvrir « Créer un groupe » sur `/dashboard/permission-groups` — la grille de permissions (une carte par catégorie, `PermissionCheckboxGrid.tsx`) dépasse largement la hauteur de la modale.
- **Résultat attendu** : en-tête, nom du groupe, la totalité des catégories de permissions (via défilement interne si nécessaire) et les boutons d'action (Annuler/Créer) restent tous accessibles, quelle que soit la hauteur du viewport.
- **Résultat observé (avant correction)** : `DialogContent` (`src/components/ui/dialog.tsx`) n'a par défaut aucune hauteur maximale ni défilement (`grid gap-4 ... p-4`, aucun `max-h`/`overflow-y-auto`) ; la modale de création de groupe n'ajoutait rien de plus (`className="sm:max-w-2xl"` uniquement) — le contenu débordait sans aucun moyen d'atteindre le bas du formulaire ni les catégories situées après la hauteur visible.
- **Cause racine** : absence de toute contrainte de hauteur/défilement sur cette modale spécifique (le composant `DialogContent` de base n'en impose pas non plus, par choix — d'autres dialogues de l'application sont plus courts et n'en ont pas besoin).
- **Correction** : `src/app/dashboard/permission-groups/PermissionGroupsPanel.tsx` seul modifié (pas `dialog.tsx`, pour ne pas changer le comportement des autres dialogues de l'application) — `DialogContent` passé en `flex max-h-[85vh] flex-col overflow-hidden`, `DialogHeader` et `DialogFooter` restent hors de la zone défilante (donc toujours visibles), seule la zone `Nom + grille de permissions` (`flex min-h-0 flex-1 flex-col gap-4 overflow-y-auto`) défile en interne. Aucune règle de permission modifiée, aucune catégorie retirée.
- **Fichiers modifiés** : `src/app/dashboard/permission-groups/PermissionGroupsPanel.tsx`.
- **Tests ajoutés** : aucun test Vitest automatisé dédié (bug de rendu CSS/scroll pur, sans surface HTTP testable — même famille qu'INC-2). Vérification manuelle en navigateur réel documentée ci-dessous.
- **Tests exécutés** : vérification manuelle Playwright (navigateur réel Chromium) sur un tenant jetable — modale ouverte à 1280×800 (desktop) : en-tête et bouton de fermeture visibles, formulaire scrollable indépendamment ; défilement programmatique jusqu'au bas du conteneur interne confirmé (`scrollHeight` 2410px contre `clientHeight` 523px) avec la dernière catégorie (« Déplacements ») et le footer (Annuler/Créer) simultanément visibles ; une permission de la première catégorie (« Agences » → « Voir les agences ») et une de la dernière catégorie (« Déplacements » → « Voir les bons de déplacement ») cochées puis le formulaire soumis avec succès (groupe créé, 2 permissions) ; fiche du groupe rouverte après création — les deux permissions cochées confirmées persistées ; répété à 390×844 (mobile) et 834×1112 (tablette), modale intégralement contenue dans le viewport sans débordement dans les deux cas. `npx tsc --noEmit`/`npm run lint`/`npm run build` verts après correction ; suite complète (`node scripts/test-grouped.mjs`) 1293/1293 verte (aucune régression, ce module n'a pas de test Vitest dédié).
- **Résultat après correction** : conforme au résultat attendu sur les trois tailles de viewport testées.
- **Risques résiduels** : aucun test de non-régression automatisé pour ce défaut précis (CSS/scroll) — une régression future ne serait détectée qu'en vérification manuelle. D'autres dialogues à contenu potentiellement long (non audités dans cette session, hors périmètre du bug signalé) pourraient présenter le même défaut si leur contenu venait à grandir.
- **Statut** : Corrigé et vérifié.
- **Validation finale** : vérifié par la séquence de tests manuels ci-dessus (2026-08-26) ; en attente de validation du propriétaire du projet sur ce rapport.

## INC-7 — BUG-005 : kilométrage de retour non validé sur le flux générique PATCH /api/locations/[id]

- **Date** : identifié et corrigé le 2026-08-26 (campagne de validation, session de reprise après interruption par limite de session).
- **Environnement** : développement/test (`xrent_dev` pour la reconstitution des données, `xrent_test` pour les tests automatisés).
- **Gravité** : mineure à modérée (aucune perte de données, mais une agence de retour sans accès à l'agence de départ pouvait enregistrer un kilométrage de retour incohérent — inférieur, égal, négatif ou non numérique — sur le seul flux qui lui est ouvert).
- **Module** : `src/lib/locations.ts` (`updateLocation`), `src/app/api/locations/[id]/route.ts` (PATCH), utilisé notamment par `LocationActions.tsx` (panneau « Réception du véhicule », agence de retour seule).
- **Préconditions** : un contrat `ACTIVE` avec un `startOdometer` connu ; un utilisateur ayant uniquement accès à l'agence de retour (`dropoffAgencyId`), donc restreint par construction au flux PATCH générique plutôt qu'à `POST /api/locations/[id]/return` (voir `canManageReturnOnly`, `src/lib/authz.ts`).
- **Données utilisées** : véhicule/contrat de test dédiés créés dans `xrent_test` par la suite automatisée (voir Test de non-régression) ; aucune donnée de la campagne RAK/CASA modifiée.
- **Scénario de reproduction** : `PATCH /api/locations/[id]` avec `{ "endOdometer": <valeur inférieure ou égale à startOdometer> }`.
- **Résultat attendu** : `Le kilométrage de retour doit être supérieur au kilométrage de départ.` (HTTP 400), aucune écriture partielle.
- **Résultat observé (avant correction)** : requête acceptée (HTTP 200), `endOdometer` enregistré tel quel en base sans aucune comparaison à `startOdometer` — seul le flux dédié `POST /api/locations/[id]/return` (`src/lib/location-return.ts`, `assertValidOdometer`) appliquait déjà cette règle.
- **Cause racine** : `updateLocation()` (`src/lib/locations.ts`) validait le niveau de carburant (`validateFuelLevel`) mais n'avait jamais reçu l'équivalent pour `endOdometer` ; la validation générique côté route (`PATCH /api/locations/[id]/route.ts`) ne vérifiait qu'un entier positif ou nul, sans comparaison au départ.
- **Correction** : nouvelle classe `InvalidReturnOdometerError` et fonction `assertValidReturnOdometer()` ajoutées dans `src/lib/locations.ts` (dupliquées depuis la même règle que `location-return.ts` plutôt qu'importées — `location-return.ts` dépend transitivement de `locations.ts` via `invoices.ts`, une importation créerait un cycle ; même raisonnement déjà appliqué à `InvalidFuelLevelError`), appelée dans `updateLocation()` dès que `endOdometer` est fourni et non nul, comparée au `startOdometer` résultant (celui fourni dans le même appel s'il change, sinon celui déjà enregistré). Message d'erreur clair, mappé en HTTP 400 dans `src/app/api/locations/[id]/route.ts`. Aucune modification partielle possible (la validation intervient avant toute écriture). Client (`LocationActions.tsx`) complété par un attribut `min` et un message d'erreur immédiat sur les deux champs kilométrage retour (panneau « Réception du véhicule » et formulaire principal), en plus de la validation serveur — jamais à sa place.
- **Fichiers modifiés** : `src/lib/locations.ts`, `src/app/api/locations/[id]/route.ts`, `src/app/dashboard/locations/[id]/LocationActions.tsx`, `src/app/dashboard/locations/[id]/page.tsx`, `src/__tests__/locations.test.ts`.
- **Tests ajoutés** : `src/__tests__/locations.test.ts`, describe « BUG-005 — kilométrage retour doit être strictement supérieur au départ » (7 tests) — kilométrage retour inférieur (rejeté 400, message exact vérifié), égal (rejeté), valeur négative (rejetée), valeur non numérique (rejetée), champ non fourni (accepté, no-op), valeur strictement supérieure (acceptée, persistée en base), et absence de modification partielle en cas de rejet (aucun champ, y compris `notes` envoyée dans la même requête, n'est écrit).
- **Tests exécutés** : fichier isolé (100/100) puis suite complète (`node scripts/test-grouped.mjs`, 1293/1293, 0 échec/timeout/résiduel) ; `npx tsc --noEmit`/`npm run lint`/`npm run build` verts. **Confirmé en direct en navigateur réel** sur le contrat n°00002 réel de la campagne (`qa.agent.casa@fictif.test`) : `endOdometer=100` (< départ) rejeté par le serveur (`PATCH .../cmta4o81l00f5m4n9dy16fif1` → 400, message affiché côté client) sans aucune modification enregistrée ; `endOdometer=28450` accepté (200), contrat passé Terminée, kilométrage/carburant persistés après rechargement — voir HANDOFF.md section 10.
- **Résultat après correction** : conforme au résultat attendu sur les 7 scénarios testés.
- **Risques résiduels** : aucun identifié — la règle est désormais appliquée aux deux flux (`POST .../return` et PATCH générique) avec le même message.
- **Statut** : Corrigé et vérifié.
- **Validation finale** : vérifié par la suite automatisée ci-dessus (2026-08-26) ; en attente de validation du propriétaire du projet sur ce rapport.

## INC-6 — BUG-004 : une location visible seulement par son agence de départ, jamais par son agence de retour (dropoffAgencyId), dans les listes/exports

- **Date** : identifié et corrigé le 2026-08-26 (campagne de validation, session de reprise après interruption par limite de session — le rapport de la session précédente ayant identifié ce défaut n'avait jamais été écrit sur disque ; confirmé par relecture directe du code et des données réelles de `xrent_dev`, pas seulement par la description transmise).
- **Environnement** : développement (`xrent_dev`, tenant de campagne réel avec agences RAK/CASA) et test (`xrent_test`, suite automatisée).
- **Gravité** : modérée (défaut de visibilité fonctionnelle affectant le flux transfert d'agence RAK→CASA — pas une fuite de données inter-tenant, mais un accès légitime refusé à tort à l'agence de retour).

- **Cause racine** : la règle de visibilité « agence de départ OU agence de retour » (Sprint 19, DOMAINRULES.md section 37) n'avait été appliquée qu'aux routes portant sur une seule location (détail, PATCH, retour) ; chaque liste/export avait reconstruit indépendamment un filtre plus étroit (`agencyId` seul), sans règle centralisée partagée — trois implémentations divergentes de la même intention.
- **Correction** : nouvelle fonction centralisée `locationAgencyScopeWhere(accessibleAgencyIds)` (fragment Prisma `OR: [{agencyId}, {dropoffAgencyId}]` ou `null`=ADMIN), définie dans `src/lib/locations.ts` (et non dans `src/lib/authz.ts` malgré la parenté avec `canAccessLocationAgency` : `authz.ts` importe `@/lib/auth`/`next-auth`, et la placer là aurait forcé tout module qui importe `@/lib/locations` — y compris les tests unitaires qui l'importent directement, hors serveur `next dev` — à charger `next-auth` transitivement, ce qui casse la résolution ESM de `next-auth/lib/env.js` hors du runtime Next.js ; découvert et corrigé pendant cette session, voir Fichiers modifiés). Adoptée par `getLocations()` (nouveau filtre `accessibleAgencyIds` sur `LocationFilters`, utilisé par `GET /api/locations`), `getContractsOverview()` (refactorée pour réutiliser la même fonction plutôt qu'une clause `OR` dupliquée), `/dashboard/locations` (liste), le widget « Retours » du dashboard (refactorée, comportement déjà correct, désormais partagé) et l'export CSV des contrats (`runLocationsExport`, dont le commentaire obsolète a été corrigé). Filtre explicite `agencyId` (paramètre d'URL, déjà vérifié par `canAccessAgency`) toujours prioritaire, comportement inchangé. Aucune règle de permission ni d'isolation tenant modifiée — `tenantId` reste systématiquement appliqué en amont dans chaque requête.

## INC-5 — `scripts/test-grouped.mjs` désynchronisé de `src/__tests__/`, 36 tests jamais exécutés par le runner recommandé (identifié et corrigé Sprint technique 4)

- **Date** : identifié et corrigé à la source 2026-08-24 (Sprint technique 4, phase d'audit)

- **Date** : 2026-08-15

- **Description** : lors de l'exécution de la suite complète (610 tests, ~30 fichiers), certaines exécutions échouent avec des `Test timed out in 20000ms`/`Hook timed out in 60000ms` répartis sur un ensemble de fichiers différent à chaque run, sans jamais d'échec d'assertion. ## INC-1 — Agent de développement ayant exécuté `git stash` sans le restaurer avant expiration de son budget de session

- **Date** : 2026-08-14
- **Environnement** : développement (copie de travail locale, jamais poussé/déployé)
- **Gravité** : majeure (risque de perte de travail important), sans impact final (entièrement récupéré)
- **Description** : pendant le Sprint 15, plusieurs agents assistants travaillaient en parallèle sur la copie de travail locale (non isolée par worktree Git). L'un d'eux, chargé d'ajouter des tests d'audit/bout-en-bout, a exécuté `git stash` (visiblement pour isoler temporairement l'état de certains fichiers avant restauration), puis a atteint la limite d'usage de sa session avant d'exécuter `git stash pop` — laissant la copie de travail dans l'état d'avant le stash (fichiers `src/lib/*.ts`, toutes les routes `src/app/api/**` retrofitées ce sprint, tous les composants `src/app/dashboard/**` modifiés, `src/components/layout/Sidebar.tsx`) alors que le stash contenait la totalité de ce travail non commité.
